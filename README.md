## Current Chrome extension package

- Chrome extension: **v1.5.34**, bundled in the dashboard's built-in Bridge Installer.
- Open Badoc Hub's Bridge Installer and choose **Download ZIP File** to generate the current package from the synchronized `extension/` sources.

To install the package, extract the ZIP, open `chrome://extensions`, enable Developer mode, choose **Load unpacked**, and select the extracted extension folder.

## Project layout
| Path | What it is |
|---|---|
| `index.html` | Markup only (~75 KB). Loads `css/app.css` and the scripts in `js/` in order. |
| `css/app.css` | All dashboard styles. Rule order matters: later blocks intentionally override earlier ones. |
| `js/NNN-name.js` | Former inline scripts, **loaded in numeric order**. Each is a classic script sharing one global scope, exactly like the old single page. |
| `js/120-app-core.js` | Main app (KPI, rider, parcel and EOD logic). Kept as one file because its functions rely on hoisting. |
| `js/050-cloud-adapter.js`, `200/210/410/520-*cloud*.js` | Firebase cloud sync. |
| `js/bridge-files.js` | Base64 map of `extension/`, lazy-loaded only when the Bridge Installer is used. **Generated** by `tools/sync_bridge.py`. |
| `sw.js` | Service worker. The `STAMP` block is generated. |
| `tools/stamp-assets.mjs` | Adds `?v=<content hash>` to every js/css URL and regenerates the `sw.js` precache list. |

**After editing anything in `js/` or `css/`, run `node tools/stamp-assets.mjs`** (CI also does this on push), so browsers fetch the changed file.
To add a script, create `js/NNN-name.js` and add a `<script src>` tag in `index.html` at the right position, then stamp.

## Assignment Task export

- Reports → Hourly AT → Assignment Task requests the native SPX feeder Assignment Task export for the selected Created Date in Asia/Manila.
- The extension waits for the export task, verifies the export type and station, then downloads the authenticated CSV by its task file path or media ID fallback.

## Batch Search Result

- Reports → Hourly AT → Batch Search Result uses unique SPX Tracking Numbers from the selected day's Assignment Task export.
- The extension opens SPX Order Tracking, submits numbers in chunks of up to 3,000, reads the result table, and returns CSV rows to Reports.
- The returned CSV keeps each input TN and marks it Found, Not Found, or Search Failed. Failed chunks are reported in the results rather than silently omitted.

## Extension version validation
The dashboard checks the installed extension package version separately from the bridge protocol version.

Minimum versions:
- Chrome: `1.5.34`
- Firefox: `69.5.17`

Both extension bridge scripts report their package version during the handshake. Missing or older package versions are rejected by the dashboard. The built-in Chrome installer package is generated from the current Chrome source package. Firefox XPI packages are generated by the repository workflow from `extension-firefox/`.

## Pickup test mode — Orders-led with exact task status and driver lookup
- The main Pickup results use Pickup Orders as the source for one row per order, ETA eligibility, seller details, and order details. The only automatic row eligibility filter is ETA = today's Philippine calendar date.
- Pickup Task records supply both the displayed **Status** and **Assigned Rider**. Match priority is **Pickup Task Number + Pickup Point ID** first. If the order has no usable Task Number, fall back to same Pickup Point ID and Assigned Time / Create Time within a 2-second tolerance.
- When multiple rows share the same Task Number, use the 2-second timestamp window to disambiguate where possible. Ambiguous matches are treated as **No Task Match**; the app never borrows status or rider information from an unrelated task.
- Task status labels are normalized for the table: `Pickup No Order` → **OnHold**, `Accepted` → **Assigned**, `Disabled` → **Cancelled**, and `Inbounded` → **Inbounded**. Other task statuses display their task label. Orders without a safe task match display **No Task Match**.
- A Pickup Order marked `Canceled` / `Cancelled` / `Disabled` is shown only when its exact matched Pickup Task is `Disabled`. Canceled orders without that matching Disabled task are excluded from the table and **Copy for Sheet**.
- The **Sync Pickup Orders + Tasks** button requests Pickup Orders first and Pickup Tasks second. If Tasks are unavailable, ETA-today orders still appear with **No Task Match** and Assigned Rider shows **Unassigned**.
- Search is a view/search control only; it does not introduce an additional data eligibility rule. The status dropdown is hidden so every ETA-today order status remains visible.
- The combined CSV and **Copy for Sheet** use the same visible Orders-led results and matched task status. Copy for Sheet continues to exclude an order already recorded as canceled/disabled in the previous Philippine day's first-sync Orders baseline, except where the exact matched task is Disabled.
- Pickup Orders exports all statuses and all bulky types, limited by the SPX export's Created Time range. The main result then filters that export by ETA only.
- The first successful Pickup Orders and Pickup Tasks exports of each Philippine calendar day establish their respective baselines. Each Order ID / Pickup Task Number keeps its first-seen status for that day; newly appearing IDs are appended without overwriting existing entries. Baselines are kept locally and in shared cloud storage.
- Each Order Number retains its on-demand **Pickup Info** action. It reads the authenticated SPX `pickup_info` endpoint and displays pickup status/times, attempt history, task/rider, geofence result, remarks, seller signature, and available photo links. It requires an open, signed-in SPX tab and does not bulk-fetch or cache order details.

## OnHold history update (November 25, 2026)

This package includes an update to **Actual Scanned by Riders** and the Forward/Return export merge:

- The export merge now uses the shared row-preservation helper, so a newer SPX status export with a blank `Pick Up Time` does not erase the original pickup timestamp used by the fixed **3:00 PM Manila** OnHold cutoff.
- The rider table now displays **Ever OnHold / Current OnHold** separately. Current OnHold follows the latest parcel status; Ever OnHold retains a dated event and rider attribution after a later status change.
- Historical OnHold events are included in rider/town breakdowns, the selected rider detail panel, and the filtered CSV export.
- The history store is browser-local IndexedDB (`BadocHubActualScannedHistoryV1`). It is **not synchronized across devices or browsers** in this package.

**Historical-data limitation:** the app can preserve OnHold events it sees after this update is deployed, and it can capture older events when the source still contains an explicit OnHold timestamp/status. It cannot reliably recreate an OnHold transition that has already been overwritten in every available export and local history.
